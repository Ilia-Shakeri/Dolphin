# راهنمای اتصال سامانه‌های بیرونی (پیامک، پست، و بعداً تلفنی)

این سند برای **هر مشتری، با هر ارائه‌دهندهٔ واقعی** نوشته شده — برخلاف
`TIARA_SMS_SETUP.md` که فقط مقادیر یک مشتری مشخص را ثبت می‌کند. اگر ارائه‌دهندهٔ
واقعی‌تان همان TIARA/payamsms.com است، مستقیم به همان سند مراجعه کنید؛ این‌جا
فقط می‌گوید **هر فیلد چه معنایی دارد و مقدارش را از کجای مستندات ارائه‌دهندهٔ
خودتان پیدا کنید**، نه مقدار یک مشتری خاص.

هیچ ارائه‌دهندهٔ خاصی در کد این محصول هاردکد نشده — دقیقاً به همین دلیل که
بشود همین یک صفحه را برای هر ارائه‌دهندهٔ واقعی پر کرد، بدون هیچ تغییر کد
(`communications/sms.py` و `sales/postal_provider.py`، هر دو «هستهٔ
provider-agnostic + یک پیکربندی HTTP عمومی» طراحی شده‌اند). این سند همان
پرکردن را برای *هر* ارائه‌دهنده‌ای توضیح می‌دهد.

---

## پیش از شروع: این‌ها را از ارائه‌دهندهٔ خودتان بگیرید

هیچ‌کدام این‌ها را حدس نزنید — این سند هم حدس نمی‌زند:

- **مستندات رسمی API** (Swagger/OpenAPI، یا حداقل یک نمونهٔ Postman/curl
  واقعی) برای عملیات موردنیاز — ارسال پیامک، یا استعلام وضعیت مرسولهٔ پستی.
- **نشانی پایهٔ سرویس (Base URL)** و مسیر دقیق هر عملیات.
- **شیوهٔ احراز هویت واقعی**: یک کلید ثابت در یک هدر؟ یک کلید در query
  string؟ نام‌کاربری/رمز که باید ابتدا توکن بگیرند (OAuth2)؟ کدام شکل را
  ارائه‌دهنده پشتیبانی می‌کند دقیقاً همان چیزی است که پایین این سند تعیین
  می‌کند کدام گزینهٔ صفحهٔ تنظیمات را انتخاب کنید.
- **شکل دقیق بدنهٔ درخواست** (برای پیامک) — نام هر فیلد، الزامی/اختیاری
  بودنش، و یک نمونهٔ واقعی پاسخ موفق/ناموفق.
- یک **نقطهٔ آزمایشی بی‌خطر** برای تست اتصال (مثلاً استعلام موجودی حساب،
  یا یک GET سبک) — چیزی که با صدازدنش پیامک واقعی نمی‌رود یا داده‌ای تغییر
  نمی‌کند.

## بخش ۱ — سامانهٔ پیامک

صفحه: `تنظیمات استقرار ▸ اتصال سامانه‌ها ▸ سامانهٔ پیامک`، یا مستقیم
`/settings/sms-provider/` (فقط مدیر پلتفرم، فقط وقتی فیچر `outbound_sms`
روشن باشد).

| بخش صفحه | فیلد | این‌جا چه می‌رود |
|---|---|---|
| اتصال سامانه | روش احراز هویت | اگر ارائه‌دهنده یک **کلید ثابت** در هدر یا بدنه می‌خواهد → «کلید ثابت». اگر باید اول با نام‌کاربری/رمز **توکن** بگیرید و آن توکن را در هر درخواست بفرستید → «OAuth2». |
| اتصال سامانه | قالب شمارهٔ گیرنده | مستندات ارائه‌دهنده نمونهٔ شماره را نشان می‌دهد (`+98912...` یا `98912...` یا `0912...`) — همان قالب را انتخاب کنید؛ خودِ این کدبیس شماره را همیشه با `+` نگه می‌دارد و این گزینه فقط شکل ارسالی را عوض می‌کند. |
| درخواست ارسال | نشانی ارسال | مسیر «ارسال پیامک» از مستندات، کامل با `https://`. |
| درخواست ارسال | قالب بدنهٔ درخواست (JSON) | دقیقاً همان شکل JSON که مستندات ارائه‌دهنده برای «ارسال» می‌خواهد، با چهار نشانهٔ این کدبیس به‌جای مقدار واقعی: `__SMS_TO__` (گیرنده)، `__SMS_BODY__` (متن)، `__SMS_SENDER__` (شمارهٔ فرستنده)، `__SMS_ID__` (شناسهٔ یکتای این ارسال، اگر ارائه‌دهنده یک شناسهٔ سفارشی/customerId بخواهد). هر فیلد دیگری که ارائه‌دهنده الزامی کرده ولی مقدار ثابتی دارد (نه از این چهارتا) را با همان مقدار ثابت بنویسید. |
| درخواست ارسال | هدرهای ثابت (JSON) | فقط در روش «کلید ثابت» پر می‌شود — هر هدری که ارائه‌دهنده برای احراز هویت می‌خواهد (مثلاً `{"X-Api-Key": "..."}`). در روش OAuth2 خالی بماند؛ هدر `Authorization: Bearer` خودکار اضافه می‌شود. |
| ورود OAuth2 | نشانی دریافت توکن، نام‌کاربری، رمز عبور | مستقیم از مستندات بخش «ورود»/«Login»/«Authenticate» ارائه‌دهنده. |
| ورود OAuth2 | پارامترهای اضافهٔ ورود (JSON) | هر پارامتر دیگری که آن مستندات کنار نام‌کاربری/رمز می‌خواهند (مثلاً `systemName`، `scope`، `grant_type`) — دقیقاً به همان نام و مقدار. |
| تست اتصال | نشانی آزمایشی | همان نقطهٔ آزمایشی بی‌خطر بالا. |

## بخش ۲ — سرویس پست

صفحه: `تنظیمات استقرار ▸ اتصال سامانه‌ها ▸ سرویس پست`، یا مستقیم
`/settings/post-provider/` (نیازمند مجوز `sales_documents.manage`).

عمداً از سامانهٔ پیامک ساده‌تر است: یک شکل احراز هویت (کلید ثابت در یک هدر)،
بدون قالب بدنه — چون این صفحه فقط **اتصال** را آماده می‌کند؛ نگاشت وضعیت‌های
واقعیِ ارائه‌دهنده روی چهار حالت پستیِ این محصول (`sales/postal.py`) یک قدم
جداست که با کد واقعی انجام می‌شود، نه با تنظیمات این صفحه (بخش «آنچه این
راهنما حل نمی‌کند» را ببینید).

| فیلد | این‌جا چه می‌رود |
|---|---|
| نشانی پایهٔ سرویس | Base URL از مستندات ارائه‌دهنده. |
| نام هدر کلید (پیش‌فرض `X-API-Key`) | نام دقیق هدری که ارائه‌دهنده برای کلید API می‌خواهد — هر ارائه‌دهنده نام متفاوتی دارد، این فیلد آزاد است دقیقاً به همین دلیل. |
| کلید API | مقدار واقعی کلید. |
| کد فرستنده/حساب | اگر ارائه‌دهنده یک شناسهٔ حساب/فرستنده جدا از کلید می‌خواهد. |
| نشانی آزمایشی | یک GET سبک برای دکمهٔ «تست اتصال». |

## بخش ۳ — تلفنی / VoIP

هنوز **هیچ صفحهٔ تنظیماتی وجود ندارد** — نه چون فراموش شده، بلکه چون هنوز
هیچ تصمیمی دربارهٔ دامنه گرفته نشده: آیا فقط ثبت خودکار تماس در پروندهٔ
مشتری کافی است، یا ضبط مکالمه هم باید باشد (که یک تصمیم جداگانه دربارهٔ
نگه‌داریِ دادهٔ صوتی می‌خواهد)، یا یک مرکز تماس/IVR کامل. تا آن تصمیم گرفته
نشود و یک ارائه‌دهنده/پروتکل هدف مشخص نشود، این ردیف در صفحهٔ «اتصال
سامانه‌ها» فقط می‌گوید «به‌زودی» — دقیقاً طبق همان قاعده‌ای که این سند خودش
هرجا می‌گوید تا مدرک رسمی ارائه‌دهنده نرسیده، چیزی حدس زده نمی‌شود.

## توالی پیشنهادی (برای هر دو بخش بالا)

۱. همهٔ فیلدها را پر کنید، **بدون** تیک زدن «فعال باشد».
۲. ذخیره کنید.
۳. «تست اتصال» را بزنید. خطا؟ پیام را بخوانید — معمولاً یا مقدار یک فیلد
   اشتباه است یا خودِ سرور ارائه‌دهنده در دسترس نیست.
۴. وقتی تست موفق شد، برگردید و «فعال باشد» را بزنید، دوباره ذخیره کنید.
۵. (فقط پیامک) از صفحهٔ «ارسال پیامک» یک پیامک آزمایشی به شمارهٔ خودتان
   بفرستید. تست اتصال فقط احراز هویت را تأیید می‌کند، نه مسیر ارسال واقعی.

## آنچه این راهنما حل نمی‌کند — عمداً (`CLAUDE.md` §۳۰)

- **دریافت پیامک ورودی از یک ارائه‌دهندهٔ واقعی.** زیرساخت داخلی آماده است
  (`communications.adapters.InboundSMSProviderAdapter`) ولی فعال‌سازی یک
  ارائه‌دهندهٔ واقعی یک **کلاس Python تازه** می‌خواهد، نه یک فیلد تنظیمات —
  چون این‌جا امضا/replay ارائه‌دهنده باید واقعاً تأیید شود، نه فقط IP مبدا
  اعتماد شود. الزامات دقیق در `BACKEND_SPEC.md`، بخش «SMS provider adapter
  activation requirements».
- **نگاشت وضعیت واقعی سرویس پست روی چهار حالت این محصول.** همان‌طور —
  یک کلاس Python تازه (`sales.postal.PostalCarrier`) می‌خواهد، چون واژگان
  هر ارائه‌دهنده متفاوت است؛ این تنظیمات فقط اتصال HTTP را آماده می‌کند.
- **کش‌کردن توکن OAuth2.** هر ارسال یک ورود تازه انجام می‌دهد. مدت اعتبار
  توکن هر ارائه‌دهنده متفاوت است و تا از مستندات همان ارائه‌دهنده گرفته
  نشود، کش‌کردن حدسی خطرناک است (توکن منقضی وسط کار).
- **تعیین دامنهٔ VoIP/تلفنی.** بخش ۳ بالا را ببینید.

هرکدام از این‌ها اگر لازم شد، باید مثل همین سند — با مدرک رسمی ارائه‌دهندهٔ
واقعی در دست — جداگانه طراحی شود، نه حدس زده.
